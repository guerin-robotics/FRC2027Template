# Brownout Analysis

The 2026 robot logged hundreds of brownouts in one event, with the battery sagging under peak draw.
Current limits in `TunerConstants` were tuned against that data. This skill finds **which mechanism
caused each sag**. It is **read-only**.

## Step 1 — Gather

Ask for the log (`.wpilog` / `.hoot`), and what happened (robot lost power, mechanism went limp,
or just a warning). Also ask: which battery, how old, and was it fully charged? A tired battery
makes every mechanism look guilty.

## Step 2 — Find the sags

From `BatteryLogger/`:

| Channel | Use |
|---|---|
| `Voltage`, `MinVoltage` | The sag itself |
| `BrownedOutNow`, `BrownoutCount` | Exact brownout times |
| `Current`, `DriveCurrent`, `Power` | Total and drivetrain draw |
| `Current/<key>` and `Power/<key>` | Per-consumer draw (each subsystem's `reportCurrentUsage`) |
| `Energy`, `Energy/<key>` | Cumulative use — a battery low at the start of a match |

List every event where voltage fell below ~7 V (or the brownout flag set), with match time. Group
events that share a cause.

## Step 3 — Attribute each sag

At each sag, rank consumers by `Current/<key>` in the preceding second. Then check what the robot
was doing (`Commands/` log, auto vs teleop, which mechanisms ran). Typical findings:

| Pattern | Meaning |
|---|---|
| Drive current spikes while accelerating or pushing | Drive supply limit too high, or acceleration limit too aggressive |
| Several mechanisms start in the same instant | Sequence start-up needs staggering |
| One mechanism pulls far above its normal draw | Stall or jam — look at its torque current and velocity |
| Sags only late in a match | Battery energy, not a mechanism — check `Energy` |
| Voltage dips but no device accounts for the current | A consumer missing from `reportCurrentUsage` — report the gap |

### Stator versus supply — do not mix them up

Only **supply** current belongs in battery and brownout math. Stator current is windings, not the
battery. At low speed under load, supply is a fraction of stator. Using stator here overstates the
draw exactly when the robot works hardest. This is the 2026 bug that inflated every power figure;
confirm each device in the analysis reports supply, and say so if one does not.

### Torque current

Under `TorqueCurrentFOC`, torque current is the control signal and is in **amps**. Use it to tell a
stalled mechanism from a healthy one drawing similar stator current. Do not treat sim torque
current as real — see `.claude/rules/02-hardware.md`.

## Step 4 — Report

Per event: time, minimum voltage, top three consumers with amps, the command or phase running, and
your confidence. Then rank causes by how many sags they explain.

For any proposed fix, state the failure mode per the safety rules: a lower supply limit trades
brownout for a slower mechanism; a higher one risks brownout or wire heating. Fix options, cheapest
first: stagger sequence starts, reduce an acceleration limit, lower a supply limit with a stated
reason, then hardware (battery, wiring, connectors).

## Hard limits

- **Never raise a current limit.** Raising one is a High-risk change needing the user's confirmation
  and a stated justification. Check which limit is actually binding (supply or stator) before
  proposing any change — raising the wrong one does nothing.
- Do not edit `TunerConstants` — it is generated by Tuner X.
- Do not remove `BatteryLogger.reportCurrentUsage()` calls.
